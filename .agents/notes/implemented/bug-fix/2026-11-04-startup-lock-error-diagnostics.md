# Agent Note: 数据目录占用错误的可诊断呈现

Status: implemented

[English](2026-11-04-startup-lock-error-diagnostics.en.md) | 中文

## Problem

同一数据目录已有 `ztask serve` 时，第二个实例只打印 `启动失败：数据目录正被进程 N 持有`。这条消息没有数据目录、没有已在运行实例的地址，也没有说明用户应该停止旧进程、直接访问旧实例，还是清理被复用的 PID；读不到持有者 PID 的异常锁目录又与活进程共用同一条路径。`acquireDataDirLock()` 本身已有锁目录和 PID，但 `LockHeldError` 只保留一行文本，CLI 也没有把启动配置带进错误路径，因此信息在错误对象边界丢失。

## Decision

`LockHeldError` 增加 `dataDir`、`lockDir` 与 `pid` 三个只读现场；`acquireDataDirLock()` 在抛出点一次性读 PID 并构造错误，不再让调用方解析消息。CLI 在 `runServe()` 捕获锁冲突，使用专门的纯函数按 `process.platform` 渲染多行提示：第一行保留原有 `启动失败：…`，随后给出数据目录、已知的管理端地址、当前平台的查看/停止命令，以及“PID 不是 ZTask 时先确认无写者再删除锁目录”的处理。`--port 0` 或读不到 PID 时不伪造地址，改用独立说明。

退出码仍为 1，锁获取/接管算法、健康检查与自动停止行为不变；呈现逻辑留在 CLI，因为服务端不知道本次启动的 host/port，也不应承担终端文案。消息与 CLI README 由单元测试和子进程集成测试共同钉住。

## Alternatives considered

把完整多行文案放进 `LockHeldError` 被放弃：服务端没有 CLI 的启动上下文，终端命令与平台判断属于呈现层，放进错误对象会让其他调用方被迫继承同一套文案。锁冲突时探测 `/api/v1/health` 并把退出码改成 0 被放弃：这会改变启动语义，在错误路径引入网络超时，而且端口被复用或实例换了端口时探测结论可能误导。自动停止旧进程被放弃：抢占活着的写者风险高于收益，也与服务端“不能假设只有自己”的约束冲突。同时打印 POSIX 与 Windows 两套命令被放弃：多数信息与当前平台无关，会给用户增加无关噪声。

## Consequences

用户拿到错误后能直接判断“用哪个地址、停哪个进程、何时清锁”，也保留了原有首行以便脚本或旧文档继续匹配。代价是错误文案成为 CLI README 与测试共同维护的契约，新增平台或调整命令时要同步；如果持有者用不同端口启动，打印的地址只是本次配置的提示，用户仍需以旧实例启动时打印的地址为准。锁行为、退出码和数据目录内容均未改变。
