# Agent Note: 小任务保存的载荷校验与可诊断错误

Status: implemented

[English](2026-11-03-subtask-save-error-reporting.en.md) | 中文

## Problem

Windows 上 `appendJsonlLine` 写入 revision 后用只读句柄调用 `FileHandle.sync()`：`FlushFileBuffers` 需要写权限，只读句柄返回 `EPERM`。每次任务保存都要追加 revision，因此 Windows 上所有保存都会失败，并被统一错误处理压成“内部错误”。

小任务保存失败时，用户只能看到“内部错误”。服务端错误处理把所有未预期异常压成同一个 `INTERNAL_ERROR / 内部错误`，既不记录请求编号与堆栈，也不区分存储损坏、目录不可写和代码缺陷；同时管理端小任务载荷没有结构校验，`subtasks.create` 为对象或包含空条目时会在遍历阶段抛 `TypeError`，被统一压成 500。前端又把可预判的表单问题（缺少小任务负责人、空进度）交给服务端，用户得到的提示与真实原因脱节。

## Decision

revision 追加改为用追加写句柄（`a`）完成整行写入与 `fsync`，不再写入后以只读句柄重开；Windows 不支持目录句柄 `fsync`，`fsyncDirQuietly` 在 Windows 直接跳过，文件内容的持久化仍由文件句柄 `sync` 完成。CI 新增 `windows-storage` 门禁，在 `windows-latest` 上构建并运行 JSONL/原子写测试，防止只读句柄 `fsync` 回归。

服务端在任务写入入口先校验小任务载荷结构：`subtasks` 必须是对象，`create/update` 必须是数组，`deleteIds` 必须是字符串数组，每个条目必须是对象；非法形状返回带具体字段与原因的 400，不进入聚合写入。未预期异常在统一错误处理器中记录请求编号、方法与堆栈，并按错误类型给出安全的中文原因：存储损坏、条目不存在、目录不可写、磁盘不足分别提示下一步动作，其余情况返回请求编号并引导重试或反馈。前端新增统一错误翻译层，把错误码、AJV 英文校验消息和请求编号变成可读提示；管理端与小任务表单在提交前就地校验描述、负责人和进度。

## Alternatives considered

直接把原始异常消息返回给用户被放弃：消息可能包含数据目录路径、内部文件结构或其他私有信息。只在前端做校验被放弃：旧客户端、脚本与并发入口仍可绕过，服务端必须保持封闭。继续把 500 统一成“内部错误”被放弃：它既不告诉用户下一步做什么，也让维护者无法凭一次反馈定位日志。把所有未预期异常都归为 400 被放弃：这会掩盖真实服务端故障。

## Consequences

Windows 上的保存链路恢复可用，Linux/macOS 的持久化语义不变；新增 Windows job 会增加一次 CI 时间。Windows 不做目录 `fsync`，元数据持久化依赖平台语义，崩溃窗口仍由 revision 尾部恢复兜底。用户能区分“填写不合法”“成员失效”“数据损坏”“目录/磁盘问题”，并拿到可检索的请求编号；维护者可以从服务端日志按请求编号定位堆栈。代价是错误处理器需要维护错误类型到用户文案的映射，新增存储错误码时要同步；旧的非法客户端会从 500 变成 400，若外部脚本依赖旧状态码需要调整。请求编号只用于诊断，不携带数据内容；响应仍不暴露文件路径。
