## §2 架构导览

**配置层（config.ts）**：`validateServeConfig`（[config.ts:65](apps/server/src/config.ts#L65)）是唯一的启动配置入口——默认 `127.0.0.1:8123`，`dataDir` 缺省走 `defaultDataDir`（:28，`ZTASK_HOME`→`~/.ztask`）。wildcard 判定（:39）把 `0.0.0.0`/`::`/空串挡在门外，这是设计 01 §3「不接受 0.0.0.0/:: 作为普通分享配置」的机械执行。`port 0` 仅在 loopback 时放行（:74-76），供测试让内核分配端口。CLI 自己不做业务校验，只做参数→`ServeConfigInput` 的映射（[serve-args.ts:17](apps/cli/src/serve-args.ts#L17)），错误处理收敛在一处。

**锁层（lock.ts）**：`acquireDataDirLock`（[lock.ts:26](apps/server/src/lock.ts#L26)）用「mkdir 的原子性」当锁——设计 04 §1 明示允许「`proper-lockfile` 或等价 mkdir 锁」。持锁者 pid 写在锁目录内的 `pid` 文件；发现 EEXIST 时读 pid：进程活着 → `LockHeldError`，死了或没文件 → 视为陈旧锁，删掉重试一次（:38）。`process.kill(pid, 0)`（:77）是零信号探测——不发送任何东西，只问"这个进程还在吗"，EPERM 也算活着（属主不同但进程存在）。

**HTTP 层（app.ts）**：`buildApp`（[app.ts:37](apps/server/src/app.ts#L37)）按固定顺序装配四件事：
1. 每请求生成 UUID（genReqId），`onRequest` 打 `listenerKind` 标（:46-49）——LAN 监听本体是 #20 的事，但标记先埋好；
2. `preHandler` 钩子（:58-71）对 `/api/v1/admin` 前缀双查 `listenerKind` 与 `socket.remoteAddress`，非本机一律 403 `ADMIN_LOCAL_ONLY`（04 §4.1 的钩子预留；admin 路由本体后续 issue）；
3. `GET /api/v1/health`（:73）匿名返回 `{status,version,uptimeSeconds}`；
4. 两个兜底 handler：错误（:79，ApiError→自带码；schema 校验→400 INVALID_REQUEST；其余→脱敏 500）与 404（:103，`/api/*` 前缀→统一 JSON `NOT_FOUND`，其余→`sendFile("index.html")` SPA 回退）。

**静态资源的关键取舍**：`@fastify/static` 以 `wildcard:false` 注册（[app.ts:55](apps/server/src/app.ts#L55)）。实测 `@fastify/static@8.3.0` 源码：`index.js:119` 显示只有 `wildcard === true`（或缺省）才注册 `GET /*` 通配路由（`index.js:125` 的 `req.params['*']` 分支）。也就是说，若不关 wildcard，未命中文件会被插件的通配路由先截走、由插件自己 404，我们的 notFoundHandler（SPA 回退）根本没有机会执行——`wildcard:false` 不是风格偏好，是 SPA 回退能工作的前提。

**生命周期层（bootstrap.ts + cli.ts）**：`serve()`（[bootstrap.ts:23](apps/server/src/bootstrap.ts#L23)）严格按 07 §1 的顺序执行本 issue 该覆盖的子集：取锁（:24）→ buildApp → `listen`。监听失败在 catch 里释放锁再抛（锁不能泄漏）。`close()` 幂等（closed 标志），先关 HTTP 再释放锁。CLI 把 SIGINT/SIGTERM 转成 `handle.close()`（[cli.ts:43-44](apps/cli/src/cli.ts#L43-L44)），保证 Ctrl-C 不留锁、不留未完成写。自动打开浏览器走 `resolveOpenDecision`（[serve-args.ts:57](apps/cli/src/serve-args.ts#L57)）：`--no-open` 优先，非 TTY / CI 环境一律不打开（对 01 §3「本机启动默认打开」的合理精化，理由已写进代码注释与 README）。

**契约层（packages/shared）**：`API_PREFIX`（[api-prefix.ts:2](packages/shared/src/api-prefix.ts#L2)）、错误码封闭集（[errors.ts:7](packages/shared/src/errors.ts#L7)，与 05 §7 表逐码对应）、DTO（[dto.ts](packages/shared/src/dto.ts)，与 05 §2.1 逐字段一致）。零运行时依赖，纯类型与常量——它是后续所有 issue 的"水电气接口标签"，不是工具箱。

## §3 数据流走查（端到端剧本）

以「管理员在本机第一次启动并访问」为剧本：

1. **敲下命令**：`pnpm serve` → `node apps/cli/dist/cli.js serve`（[package.json:23](package.json#L23)，直调产物绕开 pnpm bin 链接时机问题）。
2. **参数归一**：`parseServeArgs(["serve"])` 得 `{host:"127.0.0.1", port:8123, dataDir:undefined, open:true}`（[serve-args.ts:23-39](apps/cli/src/serve-args.ts#L23-L39)）→ `validateServeConfig` 补 dataDir 默认并拒绝 wildcard。
3. **占地盘**：`acquireDataDirLock` 在数据目录里 mkdir `.ztask-lock`，写入自己 pid。若这是第二个实例，拿到 EEXIST → 读到对方活 pid → `LockHeldError` → CLI 打印「数据目录正被进程 N 持有」exit 1（冒烟已验证）。
4. **装配与监听**：`buildApp` 注册插件与钩子；`app.listen({host,port})` 绑定 127.0.0.1:8123；CLI 打印管理 URL 与数据目录。
5. **浏览器打开首页**：GET `/` → 无路由命中 → notFoundHandler（[app.ts:103](apps/server/src/app.ts#L103)）→ 非 `/api/` 前缀 → `reply.sendFile("index.html")` → Vue 壳加载。
6. **健康卡亮灯**：App.vue `onMounted` fetch `/api/v1/health`（[App.vue:16](apps/web/src/App.vue#L16)）→ 200 `{status:"ok",version,uptimeSeconds}` → 绿点；此后每 15s 轮询（:26）。URL 用 shared 的 `API_PREFIX` 拼接——前端没有第二个地方硬编码 `/api`。
7. **有人在局域网试探 admin**：请求打到 `/api/v1/admin/folders`。本 issue 只有 loopback 监听，但钩子按 04 §4.1 全量校验：`listenerKind` 或 remoteAddress 非本机 → 403 JSON `ADMIN_LOCAL_ONLY`；本机请求则因 admin 路由未实现回落 404 `NOT_FOUND`（app.spec 两分支都有断言）。
8. **输错 URL**：`GET /api/v1/nope` → 404 JSON（:105-108），`content-type: application/json`，**绝不会**返回 index.html——SPA 与 API 的边界由前缀一刀切。
9. **Ctrl-C**：SIGINT → `shutdown` → `app.close()`（等在途请求完成）→ `lock.release()`（rm 锁目录）→ exit 0。冒烟验证锁目录消失，同 dataDir 可立刻再启动。

## §6 讨论点

### 6.1 残锁接管的「锁真空」窗口

- **位置**：[lock.ts:38-40](apps/server/src/lock.ts#L38-L40)（`rm` 陈旧锁 → 循环第二次 `mkdir`）
- **现象**：接管陈旧锁分两步：先 `rm -rf` 旧锁目录，再重新 mkdir。两步之间锁处于真空：若此刻第三个进程 mkdir 成功，原接管方会在第二次 mkdir 收到 EEXIST，此时读到的 pid 是新持有者的活 pid → 明确 `LockHeldError`，不会误判。真实竞态窗口是「两个进程同时看到陈旧锁并同时 rm」——双方都 rm 成功，随后只有一个 mkdir 赢，输的一方拿到 EEXIST + 活 pid 报错。语义正确，但删别人锁目录的动作本身依赖「pid 已死」这个判断的时效性。
- **问题**：pid 判断与 rm 之间，pid 理论上可能被 OS 复用（新进程恰好拿到同一个 pid），导致误删活锁。
- **预判**：本地单用户场景，pid 复用 + 毫秒级窗口同时命中的概率可忽略；mkdir+pid 方案是设计文档点名的等价方案。若未来要收紧：锁目录名带随机 token，rm 前校验 token 未变（即 proper-lockfile 的做法）。
- **结论**：（留空，待拍板）

### 6.2 未命中静态文件会静默回 index.html

- **位置**：[app.ts:112](apps/server/src/app.ts#L112)
- **现象**：`wildcard:false` 下，所有非 API 未命中路径（包括 `/assets/不存在.js`）都回 index.html 且状态 200。
- **问题**：JS 资源缺失时浏览器拿到 HTML 会报 MIME/语法错误而不是 404，排查构建产物缺失时不如直接 404 直观。
- **预判**：dist 由 `pnpm build` 保证完整，运行中不会缺文件；这属于 SPA fallback 的通用代价。若要更严谨，可在回退前检查 `accept` 头是否含 `text/html`（#14 接真实页面时顺手做）。
- **结论**：（留空，待拍板）

### 6.3 dev 模式没有进程级热重启，vite 依赖手动起 server

- **位置**：[package.json:23](package.json#L23)（`dev`: `pnpm -r --parallel --stream dev`）与 [apps/web/vite.config.ts:10-13](apps/web/vite.config.ts#L10-L13)
- **现象**：`pnpm dev` 并行跑各包 `tsc --watch`（编译到 dist）与 `vite`（HMR）；但 dist 变化不会重启任何 node 进程，且 vite 代理假设 8123 上已有 `ztask serve`——dev 会话需要另开一个终端先 `pnpm serve`。
- **问题**：README 承诺的开发模式体验不完整：改 server 代码要手动重启；忘起 server 时 vite 页面健康卡报"服务不可达"。
- **预判**：#14（Vue 应用壳）会把开发流变成主战场，届时统一解决（如 `node --watch` 跑 dist、或 tsx watch 直跑 src）；本 issue 的 `dev` 脚本只是把已有件拼起来。
- **结论**：（留空，待拍板）

### 6.4 全新环境 `pnpm exec ztask` 不可用（bin 链接时机）

- **位置**：[apps/cli/package.json](apps/cli/package.json#L10-L12)（bin 指向 dist/cli.js）与 CI 日志的 pnpm WARN
- **现象**：`pnpm install` 时 dist 还不存在，pnpm 建 `node_modules/.bin/ztask` 链接失败（WARN，不阻断）；`pnpm test` 先 build 后产物存在了，但 .bin 链接不会自动补建。根 `serve` 脚本已直调 `node apps/cli/dist/cli.js` 规避。
- **问题**：在全新 clone 上想直接敲 `pnpm exec ztask serve`（不经根脚本）会失败；需要再跑一次 `pnpm install` 才有 bin。
- **预判**：README 只承诺 `pnpm serve`，无实际用户路径受伤；可接受。若在意，可在 CI build 后补一步 `pnpm install`，或在 README 注明。
- **结论**：（留空，待拍板）

### 6.5 HealthPayload.uptimeSeconds 的语义口径

- **位置**：[app.ts:76](apps/server/src/app.ts#L76)（`Math.floor((Date.now()-startedAt)/1000)`）与 [dto.ts:74](packages/shared/src/dto.ts#L74)（注释「进程已运行秒数」）
- **现象**：实现计算的是「该 Fastify 实例自 buildApp 起的存活时长」，注释写的是「进程已运行秒数」。单次 serve 场景两者相等；测试里 buildApp 被反复调用时语义分叉。
- **问题**：字段口径与注释不完全一致，未来若有人在同一进程内多次 buildApp（测试/热装配），监控数值会回跳。
- **预判**：改用 `process.uptime()` 更贴注释（进程口径），或把注释改成「服务实例已运行秒数」。一行改动，无行为风险。
- **结论**：（留空，待拍板）

### 6.6 openBrowser 的错误提示只覆盖异步 error 事件

- **位置**：[cli.ts:52-60](apps/cli/src/cli.ts#L52-L60)
- **现象**：`spawn` 同步抛错走 catch 分支；子进程异步失败走 `child.on("error")`。macOS 上 `open` 几乎总在，Linux 无头机可能没有 `xdg-open`——此时用户只会看到一条「未能自动打开浏览器」日志，服务照常。
- **问题**：无。失败路径已兜底且不影响服务；仅提示文案未区分平台。
- **预判**：接受现状；Windows 已在 README 声明为手动访问。

## §9 文件级代码分析

### apps/server/src/config.ts（A，86 行）

**职责**：启动配置的唯一守门人；**变更形态**：新增。
**关键依赖**：仅 node:os/node:path——配置层零第三方，错误信息全中文并引用设计章节号（如「01 §3」），报错即文档。
**变更块分析**：`validateServeConfig`（:65-86）把"默认值填充"和"非法拒绝"写在一个函数里，顺序是 host → port → dataDir → staticRoot。两处细节：`port === 0 && !isLoopbackHost(host)` 单独成错（01 §3「0 仅用于 loopback 测试」的忠实转译）；`dataDir` 空白串报错而不静默回默认（`"  "` 不等于"没给"）。`isLoopbackHost`（:49）同时认 `localhost`、`127.0.0.0/8` 前缀、`::1` 和 IPv4 映射形式 `::ffff:127.x`——后者是 Node 在双栈 socket 上报告 remoteAddress 的真实形态，漏了它会把本机请求误判为远端。
**实现思路**：CLI 只翻译参数，配置层独揽校验——测试不必拉起 CLI 就能覆盖全部拒绝路径。
**检视发现**：无。

### apps/server/src/lock.ts（A，88 行）

**职责**：数据目录单写者锁；**变更形态**：新增。
**关键依赖**：node:fs/promises 的 mkdir 原子性——POSIX 上 mkdir 对已存在目录必定 EEXIST，这就是锁；`process.kill(pid, 0)` 作存活探测（EPERM 视为活：进程存在但属主不同）。比喻：mkdir 是"把旗子插上山头"——同一座山头只插得进一面旗；pid 文件是"插旗人留的名片"，名片上的人不在了，后来者可以拔旗重插。
**变更块分析**：`acquireDataDirLock`（:26-49）的两轮 for 循环是唯一稍绕的地方：第一轮 mkdir EEXIST 时查残锁，若是陈锁则 rm 并进入第二轮再 mkdir；第二轮再失败就绝不重试（:38 直接抛 heldMessage）——「只重试一次」避免了双活竞态下的无限循环。release（:43-46）用 `rm -f` 递归强删，天然幂等。
**实现思路**：锁、pid、接管全部收敛在一个 88 行文件；错误消息带持有者 pid 方便现场定位。
**检视发现**：见 §6.1（接管窗口）——根源是「判断-删除-重建」非原子，属 mkdir 锁方案的固有边界，设计文档明示接受该档位。

### apps/server/src/app.ts（A，117 行）

**职责**：Fastify 装配总成；**变更形态**：新增。
**关键依赖**：fastify 5（genReqId/setNotFoundHandler/setErrorHandler 三件套）、@fastify/static 8（`wildcard:false` 语义已翻源码实测：index.js:119 只有 wildcard===true 才注册 `GET /*`，:125 的通配分支被我们关掉了——所以所有未命中都归我们的 notFoundHandler）、@fastify/cookie（本 issue 未用，预埋给 #18 会话）。
**变更块分析**：三段值得逐行看。
其一，`decorateRequest("listenerKind", "loopback")` + onRequest 钩子（:46-49）：fastify 的 decorateRequest 第二参是"默认值"而 onRequest 每请求覆写——lan 值现在没有任何入口能产生（LAN 监听是 #20），但类型与钩子管线先通。
其二，Admin 钩子（:58-71）放在 `preHandler` 且对全部路由生效、按 URL 前缀触发：`listenerKind === "loopback" && isLoopbackRemote(request.socket.remoteAddress)` 双条件缺一不可——设计 04 §4.1 原文「Admin API 同时检查 listenerKind=loopback 和 remoteAddress=loopback」。注意它 throw 的是 `reply.status(403).send()` 而非抛 ApiError：钩子内直接终结响应，绕过 errorHandler 一次序列化，少一层。
其三，404 handler（:103-114）第一行就是 `url.startsWith("/api/")`——API 与 SPA 的国界线画在最前面，之后才谈回退。这正是验收标准「API 错误不返回 index.html」的实现位置。
**实现思路**：所有"统一"（统一 404、统一错误形状、统一 requestId）都压在两个兜底 handler 里，业务路由以后写起来只管抛 ApiError。
**检视发现**：`errorHandler` 对 ≥500 统一替换 message 为「内部错误」（:96-98）——内部异常细节不外泄（04 §3 要求），代价是本地排障要看日志；本 issue logger:false 无日志，#13 接存储后应同步接 logger。已知弱点，接受但记录在案。
